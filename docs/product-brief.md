# PhotoDock / 写真ドック プロダクトブリーフ（2026-09-12 更新）

製品検討セッションの結論。**このファイルが方針の原本**。
変更するときはこのファイルを更新する（会話の記憶はセッションを跨がない）。

## 1行定義

**カメラロールの棚卸し診断アプリ。全量スキャンで「見られたらまずい写真」（カード・住所・電話・スクショ内の個人情報・QR・位置情報）を洗い出し、危険度順に提示して対処（削除・非表示・位置情報除去コピー）までさせる。何も編集しない・検出内容の本文を保存しない・通信しない。**

## ここに至った経緯（結論だけ）

1. 初案は「SNS 投稿前の写り込みチェッカー」（共有シートでぼかして保存）
2. → **投稿前の習慣化は無理筋**と判断（リスクがまれで見えない / 投稿の瞬間は急いでいる / 必要な人ほど入れない逆選択）。ぼかし編集も却下
3. → 「予防」から「診断」へピボット。当初は**位置情報の地図可視化を主役**にした
4. → 再検討（2026-09-01）で**主役を「全量棚卸しスキャン」に交代**。理由: ①GPS の脅威は薄い（主要 SNS が EXIF を消す以上、漏れる経路はファイル送信だけ＝作者自身が脅威を感じられない）②地図の結果画面は自宅の位置そのものでシェアできない ③本当の爆弾はピクセル内の機微情報（カードを写した写真・身分証・書類・パスワードのスクショ）で、漏洩経路も共有に限らない（紛失・覗き見・誤送信）。ユーザーの問いを「これ、渡して大丈夫？」から「**カメラロールに、見られたらまずい写真が眠っていないか？**」に変更
5. → 実装着手後（2026-09-07）に**利用頻度を明示化**。このアプリは毎日使うものではなく「**半年に1回、気づいたときに回す**」人間ドック型。これは方針転換ではなく 3. の帰結の言語化で、以下が導かれる:
   - **初回スキャンが製品のほぼ全体**。2回しか起動されないなら学習の余地がなく、オンボーディングで説明する猶予もない。待ち時間 UX（UI 原則 3.）は装飾ではなく本体
   - **2回目は別の体験（差分診断）**になる（後述）
   - **再接触の手段は通知**であってウィジェットやコントロールセンターではない（「入口」節で優先度を修正）
   - **課金にサブスクは合わない**（「マネタイズ」節）
   - 半年空くと **OS のメジャー更新が挟まる**のが普通＝所見インデックスに Vision の世代が必要（後述）

## 検証済みの事実（前セッションで確認済み。再調査不要）

- **主要 SNS（X / Instagram / Facebook / メルカリ）はアップロード時に EXIF（GPS 含む）を除去する**。「SNS に上げた写真から GPS で自宅バレ」は基本成立しない＝そう訴求したら嘘になる
- **GPS が残る経路**: メール添付・Slack・Google Drive / Dropbox・AirDrop・LINE の「ファイルとして送信」・個人ブログ等（ファイルがファイルのまま渡る経路）
- **二層の脅威モデル**（経路チップの根拠）:
  - ファイルで渡す → **位置情報（EXIF GPS）** が漏れる
  - SNS に上げる → メタデータは消えるが**ピクセルに写っているもの**は誰にも消せない
- **Vision の顔検出はシミュレータで動かない**（code 9）。実機のみ。環境依存の検出器は「検出ゼロで続行」に設計する
- **顔の個人識別（他人かどうか）は公開 API に存在しない**。「顔がある」までしか分からない
- **他アプリの投稿ボタンへの介入・常駐監視は iOS では不可能**
- `PHAsset` のメタデータ（`location` / `mediaSubtypes` / `creationDate`）は**画像を読まずに数万枚を数秒でスキャン可能**（第1段スキャンの技術的根拠）
- スクリーンショットのレンダリング済みテキストは OCR がほぼ確実に読める（実写の斜め文字より遥かに強い）
- **`VNRecognizeTextRequest` はシミュレータで動く**（2026-09-07 実測・iOS 18.4）。顔検出（code 9 で動かない）と違って推論が通るので、**第2段の開発ループはシミュレータで回せる**
  - レンダリング済みの文字（スクショ相当）は日本語の住所を含めて**確度 1.000** で読めた。1,000×700 の画像・4行で 1.5 秒未満
  - `boundingBox` は Vision の**左下原点・0...1 正規化**。画像上端の行が `y≈0.83` で返る。`Region`（左上原点）への変換は **`y' = 1 - (y + height)`**（実測で確認）
  - 認識は**行単位**で返り、`4111 1111 1111 1111` のように**空白と区切り記号がそのまま保持される**。Luhn・電話番号・郵便番号の判定は**正規化（空白とハイフンの除去）してから**行う
- OCR は乱数を使わない推論＝**同一入力・同一設定・同一 OS なら実用上決定的**。結果が変わる要因は「入力解像度 / recognitionLevel / OS の Vision 世代 / 写真自体の編集」の4つだけ
- **`.fast` は日本語を扱えない**（2026-09-07 実測・iOS 18.4）。`supportedRecognitionLanguages` の結果:
  - `.fast` = 6言語・**ラテン文字系のみ**（`en-US` `fr-FR` `it-IT` `de-DE` `es-ES` `pt-BR`）。日本語・中国語・韓国語なし
  - `.accurate` = 18言語（`ja-JP` `zh-Hans` `zh-Hant` `ko-KR` `ru-RU` `th-TH` `ar-SA` 等を含む）
  - `VNRecognizeTextRequest.supportedRevisions` = `[1, 2, 3]` / `currentRevision` = 3
  - **帰結: recognitionLevel は常に `.accurate` 固定**。品質ノブは「入力解像度」と「対象範囲」だけになる（プリセットの定義を後述のとおり変更）
- **`VNDetectTextRectanglesRequest` を OCR の前段に置くと 3.1 倍速**（2026-09-10 実測・162枚・1170x2532・シミュレータ）。**採用済み**（`VisionOCRService` の内側。protocol は変えていない）
  - 大半の写真には文字が無く（162枚中 119枚）、OCR はそこで「探して何も見つけない」ために 270ms 使っていた。矩形検出は**読まずに文字らしい矩形の有無だけ**を見るので **15ms（OCR の 6%）**。言語非依存なので `.fast` のように日本語で困らない
  - **見逃しは実質ゼロ。** 唯一「文字ありなのに矩形0」になった1枚は、OCR が模様を「■」（確度 0.30）と誤認したもので、Policy の確度閾値 0.5 で捨てられる行だった（2026-11-19 に閾値を 0.3 にしたので今は判定まで届くが、どのルールにも当たらず所見にならない点は同じ）。無駄（文字なしなのに矩形あり）は2枚
  - **512px では使えない**（文字ありの 41/43 を落とす）。前段の解像度は OCR と同じ `maxPixelSize` を使う。判定に失敗したら OCR に回す（見逃す方向に倒さない）
  - 帰結: 3万枚の見積もりは 約2時間 → **約40分**。中断・再開が必須という結論は変わらない
- **`BGContinuedProcessingTask`（iOS 26）の規約**（2026-09-12・SDK ヘッダと公式ドキュメントで確認）:
  - launch handler の登録は「起動完了前に」の縛りから**除外**されている（一般の BGTask と違う）。最初の申告時に Infrastructure の中で登録すればよく、App に起動フックを足さなくてよい
  - 識別子は Info.plist に**ワイルドカード形式**（`com.upft.photodock.scan.*`）で置き、提出時は接頭辞 + 用途（`com.upft.photodock.scan.full`）
  - 進捗（`NSProgressReporting`）の報告は**必須**。止まって見えるタスクは OS が優先的に打ち切る
  - ユーザーが Live Activity で中止すると `expirationHandler` が呼ばれる。**App スイッチャーから強制終了されたときは何も呼ばれない**（記録が残っているので次回そのまま続きになる）
  - `.queue`（既定）は OS が混んでいると後で始まる。`.fail` は即時に始められないと失敗。申告は延命であって処理の開始条件ではないので `.queue` で待たずに処理を進める
  - `BGTask` は Sendable でない。1つの actor に閉じ込め、外とは ID だけをやり取りする（Swift 6 で actor 間に渡そうとすると拒否される）
  - **「進捗が止まった」の判定は dasd の Activity Progress Policy**（2026-09-12〜14・実機ログ4回）。こちらが `Progress` を1枚ごとに更新していても、**処理自体が止まって**約45〜64秒更新が無いと `Task has not reported progress within expected cadence, marking stalled` → `required criterion is not satisfied` → 打ち切り（`expirationHandler`）。アプリ側のログでは理由が分からず、Console.app で `dasd` を見て初めて分かった
  - **背景では GPU が使えない**: `IOGPUMetalError: Insufficient Permission (to submit GPU work from background)`。**Vision の文字認識は推論の割り当て（`setComputeDevice` で Neural Engine / CPU を指定）を変えても前処理で Metal を使う**。UIKit の背景猶予（約30秒）が切れた瞬間に Metal 呼び出しが詰まり、以後 OCR が1枚も進まない。4回とも同じ経路で、経過 81〜130 秒で打ち切られた
  - 正解は entitlement「Background GPU Access」（`com.apple.developer.background-tasks.continued-processing.gpu`）+ `requiredResources = .gpu`。ただし **個人の開発チーム（無料）では provisioning が拒否される**（"Personal development teams do not support the Background GPU Access capability"）。有料の Apple Developer Program が必要
  - **決定（2026-09-14）: `.gpu` を要求し、submit が拒否されたら継続を申告しない**（前面だけで進む。安全側）。有料プログラム加入後に entitlement を付ければ、コード変更なしで背景の継続が有効になる。`usesCPUOnly`（非推奨）で Metal を避ける実験は未実施
  - **未解決の懸念**: 背景で Vision が失敗したとき、`OCRService.recognizeText` は空配列を返すので「診断済み・所見なし」として記録に残りうる（見逃しが「安全」のお墨付きになる）。アプリを離れた直後の猶予 30 秒でも起きうる。→ **2026-11-20 対応**: OCR の結果を「読めた（0行もありうる）／失敗」に分け（`OCROutcome`）、失敗した写真は `failed` として扱う。当初案の「記録しない」ではなく **`failed` として記録する**（件数を画面に出すため。`ScanRecordPolicy` は「診断できた」以外を毎回やり直すので、次のスキャンで再試行される点は同じ）
    - 失敗とするのは「画像として復号できない」と「Vision がエラーを返した」。文字の矩形が無い写真は今までどおり「読めた・0行」
    - OCR が失敗した写真は、顔が見つかっていても診断済みにしない（文字を見ていないため）
    - 画面: 全量スキャンの件数に「診断できなかった」を出す（0件のときは出さない）。写真1枚の診断では「見つかりませんでした」ではなく「診断できませんでした」
    - **対象外**: 過去に失敗して「所見なし」と記録された写真は判別できないのでそのまま（OS の更新か写真の編集で再診断される）。顔検出の失敗は今も「検出ゼロ」のまま（シミュレータでは必ず失敗するので、同じ扱いにすると全写真が失敗になる。別に設計が要る）

## 機能構成

### 主役: 全量プライバシースキャン（二段構え）

- **第1段（数秒で完了）**: メタデータのみ全件列挙 — 位置情報付き枚数・スクショ枚数・総枚数。起動直後に「結果のある画面」を出し、第2段の計画（優先キュー・所要時間見積もり）を作る
- **第2段（漸進・進捗つき）**: ピクセルスキャンを優先度順に — **スクショ最優先**（機微情報の密度が最も高く OCR が最も効く）→ 直近 → 残り
  - OCR（`VNRecognizeTextRequest` ja+en）→ Policy が正規表現/チェックサムで分類（種類の一覧と段階は「検出する種類」を参照）
  - QR / バーコード（`VNDetectBarcodesRequest`・ペイロード分類）
  - EXIF GPS の有無
  - **N 枚を並行処理し、完了順に記録する**（2026-09-07 決定）。~~逐次より圧倒的に速い~~ → **2026-09-10 の実測で「ほぼ速くならない」ことが判明**（下記）。完了順に流す仕組み自体は進捗表示と中断のために残す
  - **並列度の実測（2026-09-10・162枚 / 1170x2532 / iPhone 16 シミュレータ）**

    | 同時実行数 | 所要 | 1枚あたり | |
    |---|---|---|---|
    | 1 | 44.5 秒 | 274 ms | 基準 |
    | **2** | **41.5 秒** | **256 ms** | 7% 改善。**既定値はこれ** |
    | 4 | 41.4 秒 | 255 ms | 変化なし |
    | 8 | **数分経っても終わらない** | — | **破綻**（テストとアプリの両方で再現） |

    **Vision が内部で全コアを使うので、外側の並列化はほぼ効かない。** 増やすと画像のデコードと推論コンテキストが同時に載ってメモリで破綻する。実際の写真は 4032x3024 とさらに大きいので、**実機ではより少ない同時実行数で危険域に入る**とみるべき。`ProcessInfo.thermalState` 連動を検討する前に、まず「増やしても速くならない」という前提に立つこと
  - **3万枚の見積もり: 256ms × 30,000 = 約2時間8分。** 一度で終わらせる設計は成り立たず、中断・再開が必須（下記の方針が正しかったことが数字で裏づけられた）
  - **プリセットの比（2026-09-11・同じ162枚・前段あり・実際のパイプライン）**: クイック（1,024px）**93ms/枚**、精密（3,000px）**125ms/枚** = **1.34倍**。画素数は6倍だが、前段の矩形検出が両方で文字なし写真を弾き、OCR の `.accurate` は1枚の固定費が大きく認識段階は行数に比例するため、差はほとんど出ない。**3万枚なら約40分 vs 約55分**。「全件精密」が初回として成立する範囲に入った（クイックの誤読が一覧に混ざり詳細で消える不整合も構造的に消える）。ただし文字が密な写真（レシート）では差が開く・実機の Neural Engine で比は変わる → **実機（iPhone 15 Pro Max・端末にある 709 枚・本物の写真）で計測: クイック 95ms/枚、精密 155ms/枚 = 1.63倍**（67秒 vs 110秒。iCloud のみの 2,648 枚は一瞬で終わるので合計にほぼ影響しない）。診断1枚あたりはシミュレータと同程度で、前段が大半を弾くため Neural Engine の差は出にくい
  - 全件を一度に `addTask` しない（3万タスクを作ることになる）。同時実行数を保ちながら「1つ完了したら次を1つ投入」で流す
  - 優先度は**投入順**で守る。完了順は前後するので、ライブ積み上げの表示順は厳密には優先度順にならない（投入が優先度順なら「スクショから先に結果が出る」体験は保たれるので実害なし）
- **スキャン設定**（2026-09-07 に `.fast` 非対応の実測を受けて改訂 → **2026-09-11 に「当面は精密のみ・プリセットは UI に出さない」に変更**。実機で精密はクイックの 1.63 倍で済み、記録があるので払うのは初回だけ。クイックの誤読が一覧に混ざり詳細で消える不整合も構造的に消える。`ScanQuality` の型と記録の品質は残す — 将来解像度を上げるときの再診断判定に使う）: ~~プリセット2つ~~「クイック診断」（**accurate × 低解像度**）/「精密診断」（**accurate × 高解像度**）＋対象範囲（すべて / スクショのみ / 期間）。**recognitionLevel は両方 `.accurate` 固定**で、プリセット間の速度差は**縮小率だけ**で作る（対象範囲はプリセットとは独立したユーザーの選択）。Vision の用語は UI に出さない。モード選択時に推定時間を表示（枚数 × モード別の1枚あたり実測シード値）
  - 対象範囲（すべて / スクショのみ / 期間）は**ユーザーが選ぶフィルター**として提供する。**既定は常に「すべて」で、全量を諦める方向の設計変更はしない**（2026-09-07 決定）。カードを写した写真・身分証・書類は**スクショではなく撮影画像**であり、そこを外すと1行定義が崩れる
  - `.fast` を失った速度は「対象を減らす」以外で埋める: ①**入力解像度の縮小**（精度とのトレードオフを Phase 0 で測る）②**並列度**（複数枚を同時に OCR。TaskGroup で同時実行数を制御。上限は熱と電力の制約を実機で測って決める）③**漸進提示**（優先キュー順に結果を先に出す＝待ち時間を体験にする既存方針）④**中断・再開**（一度で終わらせる必要をなくす）
- **診断中の表示**: 残り枚数 / 総枚数・残り時間（**実効スループット**＝直近の一定期間に完了した枚数 ÷ 経過時間、× 残り枚数。純粋関数 → Policy）・**所見のライブ積み上げ**（「危険 n 件」がスキャン中に増えていく）
  - 「1枚あたりの所要時間の移動平均 × 残り枚数」**ではない**（2026-09-07 修正。並行処理では1枚あたりの時間が同時実行数の分だけ伸びるので、そのまま掛けると**同時実行数の倍だけ過大に見積もる**。「あと40分」と出して10分で終わる表示になる）
    - **2026-09-10 追記: この懸念は実際には起きない。** 並列化がほぼ効かない（上記の実測）ため、同時実行数を上げても1枚あたりの時間は伸びない（274ms → 256ms）。**素直に「完了枚数 ÷ 経過時間 × 残り枚数」でよい**。ただし式の形は実効スループット方式のまま維持する（並列が効く環境に変わっても壊れないため）
- **中断・再開**: 所見インデックスがチェックポイントを兼ね、未スキャン分から再開。~~長時間スキャンはフォアグラウンド前提（バックグラウンドはサスペンドされる。スキャン中は画面スリープ抑止）~~ → **2026-09-12: `BGContinuedProcessingTask`（iOS 26）でアプリを離れても診断が続く**。全量スキャンの開始時に「診断する写真がある」ときだけ OS に申告し、1枚ごとに進捗（画面のヘッダと同じ「N / M 枚」）を報告する。OS は Live Activity に進捗を出し、ユーザーはそこから中止できる。中止・打ち切りで全件流れ切らなかったときは画面に「診断が途中で止まりました（残り N 枚）」と出し、途中の数字を完了として見せない。「続きを診断」は再診断と同じ操作で、記録のある分は一瞬で流れるので実際に続きから走る。全件が記録で済む2回目以降は申告しない（一瞬で終わる処理に Live Activity を出さない）。申告できない環境では前面で続ける（申告は延命であって結果を変えない）。**写真詳細を開いている間も診断は続く**（View の `.task` は子画面を push しただけでキャンセルされるので、State が自前の Task で回す）。`UIBackgroundModes` は不要だった（実機で submit が通り、task も渡った）。**ただし 2026-09-14 時点では背景の継続は実質オフ**: Vision の OCR が背景で GPU を使えず止まるため、`.gpu` を要求して拒否されたら申告しない（詳細は「検証済みの事実」の BGContinuedProcessingTask の項）。有料プログラムで entitlement を付けたら自動で有効になる
  - 並行処理なので「どこまで進んだか」の数字では表せない（5枚目が済んで3枚目が未完という状態が普通に起きる）。「**記録がある = 済み**」の集合で表すので順序は不要
  - **1アセット1トランザクション**で書く。途中で落ちても部分書き込みが残らないようにする（冪等なので、書けていない分は次回そのまま再スキャンされる）

### 結果票（2026-11-25 決定・画面の作り直し）

機能の確認用に組んだ最小限の画面を、**「検診の結果票」を軸に作り直す**。アプリの名前（ドック）とそのまま噛み合い、開いた瞬間に「これは検診だ」と伝わる。上の3階層ドリルダウンの入口（診断ホーム）を、数字のサマリーから結果票に置き換える。

モックは3方向（結果票／ダッシュボード／1枚ずつ仕分け）を作って比べた。採ったのは結果票。ダッシュボードは「分類を説明しない」方針から最も遠く、仕分けは所見が多いと終わらない（項目の中の進め方として後で取り込む余地は残す）。

- **ホームは結果票**。起動したら前回の記録から結果票を出す（診断はしない）。それまでのホームは毎回「◯枚を診断」だけで、前回の結果が出なかった
- **総合判定は3段階**: A＝所見なし（要確認がすべて対応済みの場合を含む）／ B＝要確認あり／ C＝危険あり。人間ドックは5段階だが、判定の根拠が「危険」と「要注意」の2種類しかないので、3段階が正直
- **表は項目（種類）ごと**に「判定・枚数」を並べる。判定は 所見なし／要確認／危険／対応済み。「要注意」は結果票の上では「要確認」と書く（検診の言葉に合わせる。severity の名前は変えない）
- **枚数の数え方**: 総合判定は**写真の枚数**、表は**項目ごとの枚数**。1枚に住所・電話番号・郵便番号が写っていれば3つの項目に出るので、表の合計は写真の枚数より多くなる
- **顔の写り込みは「参考」**として表には出すが、総合判定には数えない。実機（2026-11-20・853枚）で所見 51 枚のうち 42 枚が顔で、判定に入れると顔だけで B になる。顔の閾値が仮置きである間の扱いでもある
- **対応すると判定が上がる**。非表示・削除・「問題なしにする」を選んだ写真は「対応済み」になり、項目の要確認が減って総合判定が上がる。対応状況は新しく保存する（写真の ID と選んだ対応だけ。本文は保存しない方針のまま）
- **診断中は結果票が埋まっていく**（UI 原則3「待ち時間を体験にする」）。「アプリを開いたままに」の注意と中断を置く
- **初回は、写真へのアクセスを求める前に3つの約束を見せる**（端末の中だけ／書き換えない／読み取った文字を残さない）
- **見た目は `Support/Theme/` を通す**。色は役割の名前（`ground` / `ink` / `danger` …）で、ライトとダークの両方を持つ。文字は iOS の標準書体をテキストスタイルに乗せ、端末の文字サイズの設定に追従させる（フォントは同梱しない）。文字と地の組み合わせはコントラスト比 4.5 以上をテストで保つ（`ThemePaletteTests`）

段階1で決めたこと（2026-11-25）:

- **結果票に数えるのは、今ライブラリにある写真の記録だけ**。写真アプリで消した写真の記録は残っているので、数えると枚数が合わなくなる
- **ホームを開くときは、アクセスの確認ダイアログを出さない**（今の状態を読むだけ）。初回は約束を見せてから聞くため
- **「新しい写真 ◯ 枚」は、記録が無い・編集された・診断の世代が古い写真**。iCloud にあって取れなかった写真は毎回試すが、ここには数えない（数えると 2,000 枚がいつまでも「新しい写真」になる）
  - **2026-11-26 修正: 取れなかった記録は、判定ルールの版が変わっても「新しい写真」に数えない**。版を先に見ていたので、ルールを変えた直後だけ iCloud の 2,169枚が新しい写真に戻り、ボタンが「3,053 枚を診断する」になった（診断できるのは端末にある 884枚）。取れなかった記録は「診断が古い」のではなく「診断していない」ので、版や編集日時より先に見る
- 表の行は全種類ぶんの8行で固定（カード番号 / 認証情報 / 身分証の番号 / 住所 / 電話番号 / メール / 郵便番号 / 顔の写り込み）。所見が無い項目も「所見なし」として出す
- **診断中の画面は、ホームと同じ結果票の表を1件ずつ埋める**。進捗の集計（`ScanSummary`）は結果票（`ScanReport`）と同じものを数えていたので、結果票に一本化して消した
- **診断の途中では、所見のない行を「所見なし」と書かない**（診断中は「確認中」、止まったあとは「未完了」）。見ていない写真まで問題なしと読めてしまうため。「所見なし」と総合判定を出すのは、全件が流れ終わってから
- **所見のあった項目は、診断中から開ける**（それまでの画面は所見のある写真が下に増えていった。数十分かかる処理なので、終わるまで見られないのは長すぎる）。項目を開いている間も診断は続く
- **残り時間は「今回診断した枚数 ÷ 経過時間 × 残り」**（`ScanProgressPolicy`）。記録を再利用した写真は数に入れない（一瞬で流れるので、入れると残りがほぼ 0 秒と出る）。今回診断した記録かどうかは、記録の日時が開始より後かで見分ける。10 枚・3 秒たつまでは出さず、表示は分の単位に丸める
  - **2026-11-26 修正: 一瞬で終わる写真は、速さにも残りにも数えない**。実機（3,053枚・うち iCloud のみ 2,169枚）で、開始 10 秒に「あと約 6 分」と出て 2 分で終わった。iCloud にあって端末に無い写真は取れないことがすぐ分かるのに、端末にある写真と同じ速さで見積もっていたため（端末にある新しい写真が先に流れるので、平均しても合わない）。速さは「画像を読むところまで進んだ枚数 ÷ 経過時間」、残りは「これから実際に診断する見込みの枚数」（ホームのボタンと同じ値: 新しい写真 + 取り寄せを許可していれば iCloud のぶん）にした。端末に無い写真は「すぐ」でも 0 秒ではない（修正後の実機で、端末の 885枚を診断し終えたあとに iCloud の 2,169枚が 25秒かかり、「あと 1 分以内」が 78秒続いた）ので、1枚 0.012秒の実測値で残りに足す。記録が1件も無い初回は見込みが全件になるので、iCloud の写真が多いと長めに出る（どの写真が端末にあるかは、試すまで分からない）
- **画面の「中断する」は、OS の打ち切りと同じ扱い**（途中の数字を完了として見せず、「続きを診断する」で記録のある分を飛ばして再開する）
- 終わったあとの「診断できていない写真」は枚数だけを出し、内訳と iCloud の切り替えはホームの結果票に置く（同じ説明を2か所に持たない）

段階2で決めたこと（2026-11-26）:

- **項目の一覧は、写真1枚を1行で出す**（それまでは正方形のサムネイルの格子）。サムネイル・撮った日・その写真に写っている種類の札を並べる。「住所の写真」に電話番号も写っていることが、開く前に分かる

- 対処のボタンと「未対応 / 対応済み」の切り替えは段階3

段階3で決めたこと（2026-11-26）:

- **実機で確かめた iOS の確認**（iPhone 15 Pro Max・ダミーの画像で試した）:
  - 非表示: 「"PhotoDock"にこの写真を非表示にすることを許可しますか?」［許可しない／非表示］が毎回出る
  - 削除: 「"PhotoDock"に写真N枚の削除を許可しますか?」に続けて、iCloud とすべてのデバイスから消えること・「最近削除した項目」で最大30日は戻せることが出る。［許可しない／削除］
  - 「許可しない」を押すと `PHPhotosErrorDomain` の 3072 が返る（失敗ではなく、ユーザーがやめた）
  - **非表示にした写真は、`includeHiddenAssets` を指定してもアプリから取れない**。非表示にする前に取っておいたオブジェクトでなら、削除はできた
- **アプリ側では確認を重ねない**。非表示も削除も iOS が聞き、削除の影響（iCloud・30日）も iOS が説明するため
- **対応状況は、スキャン済み記録とは別に保存する**（`PhotoDisposition` / `Dispositions.store`）。記録は消しても診断し直せば戻るキャッシュだが、対応はユーザーが決めたことで、消えたら戻せない。持つのは写真の ID・選んだ対応・決めた日時・写っていた種類だけ
  - 種類を持つのは、非表示・削除した写真がもう読めないため（どの項目の「対応済み」に数えるかを、対応の側に残す）
- **対応が効いている条件**（`ScanReportPolicy.isActive`）:
  - 「問題なし」: 写真がライブラリにあり、決めたあとに編集されていないあいだ。編集されたら未対応に戻す（写っているものが変わりうる）。判定ルールが変わっただけでは外さない
  - 非表示・削除: 写真がライブラリから見えないあいだ。写真アプリで非表示を解除する・「最近削除した項目」から戻すと、未対応に戻る
- **数え方**: 対応済みの写真は危険・要確認に数えず、項目ごとの「対応済み」と `handledPhotos` に数える。項目は、未対応が1枚も無く対応済みがあれば「対応済み」。顔だけの写真は、対応しても写真の枚数（総合判定の側）には数えない（もともと数えていない）
- 取り消せるのは「問題なし」だけ。非表示と削除は写真アプリで戻してもらう
- まとめて対処はしない（1枚ずつ）。誤操作の影響が大きいので、使ってみてから考える
- **「問題なしにする」の画面**（2026-11-26・段階3の2本目）:
  - 写真詳細の下にボタンを置く。押すと「未対応に戻す」に変わる。**保存できたときだけ表示を変える**（できていないのに対応済みと見せると、次に開いたとき未対応に戻って見える）
  - 項目の一覧の「未対応 / 対応済み」の切り替えは、**両方があるときだけ出す**。片方しか無ければ、切り替えの状態によらずそちらを出す（「対応済み」を見ている最中に取り消して0枚になり、一覧が空になる不具合を実際に出した）
  - 結果票の表は、対応済みの項目には対応した枚数を出す（未対応の 0 を出すと、何も無かったように見える）
  - 総合判定 A で対応済みがあるときは「確認が必要だった N 枚は、すべて対応済みです」と書く（最初から無かった場合と言い分ける）
  - 診断中の画面でも同じ操作ができる。対応を変えたら、そこまでに流れた記録から結果票を作り直す

- **非表示・削除の画面**（2026-11-26・段階3の3本目）:
  - 写真詳細の下に、上から「非表示アルバムへ移す」（主）「削除する」（副）「問題なしにする」（文字だけ）。写真を動かさない対応は控えめに置き、取り違えないようにする
  - **順序は「ライブラリを書き換える → 実行されたときだけ対応として保存」**（`RemovePhotoUseCase`）。「許可しない」が選ばれたら何も変えず、失敗の文言も出さない
  - 対応の保存に失敗しても、結果は「実行された」と返す。写真はもう動いていて取り消せない。その写真は結果票から消えるだけで、対応済みには数えられない（数が1つ合わないが、嘘は出ない）
  - 実行したあとは、同じ画面から続けて操作させない（非表示にした写真は、もうアプリから見えない）。「一覧に戻る」だけを出す
  - 項目の一覧の「対応済み」には、非表示・削除した写真の**枚数だけ**を出す（サムネイルは出せない）。どこで確かめられるか（写真アプリの「非表示」「最近削除した項目」）を添える
  - 診断中の画面で非表示・削除したときは、その画面が持っている写真の一覧から外す（一覧は診断を始めた時点のものなので、外さないと、もう無い写真が未対応として残る）
  - シミュレータ（英語）での確認の文言: "Allow "PhotoDock" to hide this photo?" / "Allow "PhotoDock" to delete this photo?"。ボタンの並びは「やめる」「進める」の順で、実機（日本語）と同じ

- **実機で出た不具合: 対処のあと、項目の一覧からホームに戻れなくなる**（2026-11-26・iPhone 15 Pro Max）:
  - 非表示・削除のあと「一覧に戻る」で一覧に戻ると、戻るボタンを押しても一覧のままだった（2回試して2回とも。アプリを起動し直せば、結果票は正しい）。**シミュレータでは起きなかった**
  - 直し方: 写真の行に遷移（`NavigationLink`）をぶら下げるのをやめ、「開いている写真」を一覧の画面が持つ（`navigationDestination(item:)`）。行は、対処すると一覧から消える。消える行に遷移を持たせない
  - 直したあとの実機: 同じ操作（削除 →「一覧に戻る」→ 戻る）で戻れた。「問題なし」の付け外しも、待たずに戻る操作を含めて12回とも戻れた
  - **原因は特定できていない**。行が消えることが原因という見立てで直し、同じ操作では再現しなくなったが、仕組みまでは確かめていない。直したあとのビルドでも、新しい写真を診断した直後に1回だけ戻れなかった（どの画面で止まったかを記録しておらず、その後は再現していない）

**郵便番号は、長い数字の並びの一部であるときは拾わない（2026-11-20 決定）**

画像での実測で、`市場1234-5678-9012` と `注文番号 20261119-00123` が郵便番号になった。判定が「3桁-4桁」を行のどこにでも当てていて、注文番号や伝票番号の途中（`234-5678` / `119-0012`）に一致していた。

- 直前が数字かハイフン、または直後が数字か「ハイフン + 数字」なら、長い並びの途中とみなして拾わない
- **直前の英字は除外しない**。OCR が `〒` を `T` と読むことがあり、英字を条件に入れると `T150-0041` を見逃す。代わりに `A123-4567` のような型番は拾ったままになる（要注意どまりなので許容）
- `〒` や「郵便番号」の語は要求しない（宛名や名刺は `150-0041` だけを書くことが多い）
- 電話番号の同じ弱点は同日に対応（下記）

**電話番号は前後と桁数の合計を見る（2026-11-20 決定）**

郵便番号と同じく前後を見ていなかったほか、固定電話の判定が桁数の合計を見ていなかった。

- **長い数字の並びの一部は拾わない**（`注文番号 1209012345678` / `伝票 1203-1234-5678`）。条件は郵便番号と同じ（直前が数字かハイフン、直後が数字か「ハイフン + 数字」）
- **ハイフン区切りの固定電話は合計がちょうど10桁**。市外局番の長さによらず10桁なので、「月-日-年」の日付（`01-02-2026`）や桁の合わない番号が落ちる
- **末尾は3〜4桁**。4桁固定だったのでフリーダイヤル（`0120-123-456`）とナビダイヤル（`0570-012-345`）を見逃していた
- `050`（IP 電話・11桁）は携帯（`070` / `080` / `090`）と同じ判定に入れる
- 割り切り: 直前がハイフンの番号（`A-03-1234-5678`）は拾わない。ハイフンなしの固定電話（`0312345678`）、空白や括弧区切り（`03(1234)5678`）は対象外のまま

**カード番号のマスクは、番号そのものの末尾4桁だけを残す（2026-11-20 決定）**

マスクが「行に出てくる数字全体の末尾4桁」を残していたので、番号の後ろに有効期限やセキュリティコードがあると、残る数字がそちらに移っていた（`4111 1111 1111 1111 12/28` → `**** **** **** **** 12/28`）。どのカードか分からず、期限がそのまま表示されていた。

- 判定で見つけたカード番号の位置を使い、**番号の末尾4桁だけを残す**（`**** **** **** 1111 **/**`）
- **同じ行の他の数字はすべて伏せる**。有効期限とセキュリティコードは「どのカードか」の識別に役立たず、表示すると診断アプリ自身が漏洩源になる
- 1行に番号が複数あるときは最初の番号の末尾だけを残す
- 判定結果（種類と危険度）は変えない
- 電話番号と身分証番号のマスクも同日に同じ方針へ（`TEL 03-1234-5678 内線 123` → `TEL **-****-5678 内線 ***`、`AB1234567 2030-01-15` → `AB***4567 ****-**-**`）。1行に電話番号が複数あるときは最初の番号の末尾だけを残す

**有効期限とつながったカード番号は、期限の「月」を切り離して判定する（2026-11-20 決定）**

OCR が番号と有効期限の間の空白を落とすことがある（`No. 4012888888881881 12/28` → `No.401288888888188112/28`）。番号と月がつながって18桁になり、Luhn に落ちて見逃していた。

- 数字の並びの直後に `/` と**ちょうど2桁か4桁**の数字が続き、並びの末尾2桁が 01〜12 のとき、その2桁を別のかたまりに分ける
- 分けるのは候補を作るところまで。カード番号かどうかは今までどおり Luhn とブランドの番号帯・桁数が決めるので、誤検出はほぼ増えない
- 実測（Mac 本体の Vision・カード番号を含む行12種 × フォント5種 × 大きさ/ぼかし/傾き6通り = 360枚）: 修正前の見逃しは5枚。うち**期限とつながった2枚**がこの対応で拾える
- **直さないもの**
  - セキュリティコードとつながった番号（`4242424242424242123`・1枚）: 19桁のどこで切るかの手がかりが無い。先頭16桁を切り出すと、長い通し番号からカード番号を作ってしまう
  - 数字の読み違い（`5105185105105100`・2枚）: 判定側では直せない
  - 4桁区切りの途中の空白が落ちたブランド不明の番号（`1234 56781234 5670`）: 「8桁 + 8桁」を許すと、日付を2つ並べた行（`20261119 20261120`）の1割がカード番号になる

**確度の閾値を 0.5 から 0.3 に下げる（2026-11-19 決定）**

画像を作って本物の Vision に通す実測（PR #1〜#4 の検証）で、正しく読めた行が判定の前に捨てられていると分かった。

- Vision（`.accurate`・ja+en・言語補正なし）の確度は **0.3 / 0.5 / 1.0 の3段階**しか返らない（シミュレータ iOS 26.2 と Mac 本体の両方で同じ）。「検証済みの事実」の「確度 1.000 で読めた」は一部の行の話で、同じ画像でも行によって 0.3 や 0.5 になる

**判定の入口で全角とハイフンの異体を半角に寄せる（2026-11-17 決定）**

「検証済みの事実」に「判定は正規化してから行う」と書いていたが、正規化が効いていたのは認証情報のラベル語だけで、電話・郵便番号・住所・メール・パスポートは生の文字列に半角の `[0-9]` と `-` を当てていた。全角数字や、見た目の同じ別のハイフンで書かれた行を見逃していた。

- `FindingPolicy.classify` の入口で1回だけ正規化し、全種類の判定がその結果を見る（`String.normalizedForMatching`）
- 全角の英数記号と全角空白を半角へ。ハイフンの異体（`‐` `‑` `‒` `–` `—` `―` `−`）を `-` へ
- **長音記号（`ー` `ｰ`）は数字に挟まれているときだけ `-` へ**（`090ー1234ー5678`）。無条件に変えると「パスワード」が壊れる。カタカナには触らない
- 文字は1対1で置き換える（文字数と位置が変わらない）ので、**マスクも正規化後の行に対して行う**。判定は正規化後・マスクは元の文字列、と分かれていると、全角のメールアドレスを判定では拾えるのにマスクでは見つけられず、本文がそのまま `maskedText` に出ていた
- 対象外: 漢数字（`一丁目`）、丸数字、空白や括弧で区切った電話番号（`090 1234 5678` / `03(1234)5678`）

**カード番号は「連続する数字のかたまりの組」から探し、ブランドの形を照合する（2026-11-17 決定）**

それまでは行全体から空白とハイフンを除いて数字を1本につなげ、13〜19桁で Luhn が通ればカード番号としていた。2つの穴があった。

- **見逃し**: 隣の数字を巻き込む。`4111 1111 1111 1111 12/28`（有効期限）は18桁になって Luhn に落ちる
- **誤検出**: Luhn は10個に1個の数字列が偶然通る。無関係な数字がつながって13〜19桁になれば、その1割を「写っています」と断定していた。45 / 49 で始まる13桁の JAN コード（商品バーコードの数字）も対象に入っていた

変更後:

- 数字のかたまりを区切りごとに保ち、**連続するかたまりの組**を候補にする。かたまり同士をつなぐのは空白とハイフンだけ（合わせて3文字まで）
- **Luhn が通り、番号帯と桁数がブランドに合う → 危険**（Visa 16/19・Mastercard 16・American Express 15・Diners Club 14・JCB 16・Discover 16・銀聯 16〜19）。Visa の13桁は載せない（発行されなくなって久しく、JAN コードと衝突する）
- **Luhn が通り、ブランドには合わないが4桁×4で書かれている → 要注意**（表に無いブランドの受け皿。書式の一致だけなので断定しない）
- 残る誤り: 区切りなしで他の数字と直接つながった番号（`411111111111111112`）は切り出せない。表に無いブランドで4桁×4以外の書き方のカードは拾えない

**住所の番地は「市区町村の文字の後ろ」にあるものだけを見て、日付と電話番号を除く（2026-11-17 決定）**

それまでは「市・区・町・村のどれか1文字が行のどこかにある」かつ「数字-数字-数字 / n丁目 / n番地 が行のどこかにある」で住所としていた。`横浜市 2026-09-12`（日付）や `渋谷区役所 03-1234-5678`（電話番号。住所を電話より先に試すので住所が取っていた）が住所になっていた。

- 番地は**市区町村の文字より後ろ**にあるものだけを候補にする（住所は「市区町村 → 町名 → 番地」の順に書く）
- `1-2-3`（部屋番号つきの `1-2-3-405` も可）: **0 で始まる数字を含む並びは番地ではない**（日付の月日か電話番号）。0 埋めの無い日付（`2026-9-12`）と、3つ合わせて10桁を超える並び・5連以上（通し番号）も除く
- `4-5`（丁目の無い町）: **町名に直接続くときだけ**番地とみなす（`万町4-5`）。空白や記号の後ろの2連は時刻の範囲や点数のことが多い。それまで2連は一切拾っていなかった
- 漢字の書き方に `1番2号` を追加（`n丁目` / `n番地` は従来どおり。`3番線` は拾わない）
- 残る誤り: 「市場」「区分」「町内会」や姓（市川・町田・村上）の文字も市区町村の文字として数える。`区間1-2` のように町名でない語に2連が直接続くと住所になる。市区町村が1行目・番地が2行目の住所は拾えない（判定が行単位のため）

**ラベル語だけでは危険にしない（2026-11-17 決定）**

ラベル語は値が写っていない画面にも出る（ログイン画面の「パスワードを忘れた方」、設定画面の「パスワードを変更」）。スクショは最優先で診断する対象なので、ラベル語だけで危険にすると危険の件数がこれで膨らむ。「severity は検証可能性で決める」にも合わない。

- **ラベルの直後に値らしい文字列が続く → 危険**。値は「空白を含まない半角の英数記号の並び・4文字以上」（全角は半角に寄せてから見る）。`:` / `=` で区切られていればそのまま値とみなし、区切りが無いときは数字を含む並びだけを値とみなす（`Password reset` のような英語の UI 文言を値と取り違えないため）
- **ラベルだけ → 要注意**。所見から落とさないのは、値が次の行にある付箋やルーターのラベルを拾うため（判定は行単位なので、次の行の値は見えない）
- 伏せ字の入力欄（`Password: ********`）は値ではない
- 取りこぼしは「危険に上がらない」方向にだけ出る（要注意としては残る）
- 残る誤り: `Password: Required` のように区切り記号の後ろに設定値が続く行は危険になる。ログイン画面のスクショは引き続き要注意として数えられる

**見逃しは「安全」の誤ったお墨付きになる。** ゼロ件の表示は必ず「見つかりませんでした」とし、「安全です」と断定しない（UI 原則の「断定調を避ける」がここに効く）。

**2つの原則**

- **severity は検証可能性で決める**（恣意的に割り当てない）。チェックサムが通ったもの（カード番号・マイナンバー・免許証番号）は「写っています」と**断定してよい**。書式が一致するだけのもの（郵便番号・住所・パスポート番号）は「〜のような文字列が写っています」に留める。UI 原則「断定調を避ける」を、種類が増えても一貫した基準で満たせる
- **組み合わせで危険度が上がる**。氏名・生年月日は単体ではほぼ無害だが、**氏名 + 生年月日 + 住所が同じ写真に揃えば本人確認書類**。severity を「kind ごとの固定値」ではなく「同じ写真に何が揃っているか」で決める複合判定が必要になる（brief の「判断ルールが増えたら Policy 行き」に該当）

### iCloud 最適化への対応（2026-09-07 決定・製品の分かれ目）

「iPhone のストレージを最適化」がオンだと**端末に元ファイルがなく、縮小版しか残らない**（写真アプリで古い写真を開くとロードが走るのがこれ）。写真が多い人ほどこの設定なので、**例外ケースではなく多数派の状態**として扱う。

- **既定ではダウンロードしない**（`isNetworkAccessAllowed = false`）。~~1枚3MB × 3万枚 = 90GB で現実的でなく~~ → **2026-09-10 実測: 元ファイルは平均 1.6MB、`requestImage(targetSize: 1024)` で取れるサーバ側の縮小版は 287KB（JPEG換算）・0.50秒/枚**。「Wi-Fi 接続中に限りダウンロードして診断」のオプトインは ~~Phase 2 以降の検討~~ → **Phase 1 に前出し**（下記の実測で 80% が端末内では診断不能と分かったため。2,682 枚で約22分・約750MB、3万枚で約4時間・約8GB）。時間は往復の遅延で決まり縮小版でも元ファイルとほぼ同じ（0.50 vs 0.66秒）なので、**縮小版を選ぶ理由は容量**。既定オフ・Wi-Fi のみ・進捗と中断あり、が条件 → **2026-09-11 実装**: ホームのトグル「iCloud の写真も診断する」（既定オフ・`@AppStorage`）。全量スキャン開始時に `NWPathMonitor` で1回判定し、従量課金（`isExpensive`）か低データモード（`isConstrained`）なら通信しない。取るのは元ファイルでなく**要求品質（3,000px）のサーバ側縮小版**。途中で回線が切れた分は「取れなかった」記録になり次回再挑戦される
  - **通信量の訂正（2026-11-20・実機で Wi-Fi の受信量を計測）**: 上の「287KB」「約750MB」「約8GB」は、受け取った画像を JPEG にし直した大きさから計算した値で、**通信量ではなかった**。iCloud にしかない写真を全体から等間隔に 60 枚拾い、大きさごとに別々の 20 枚で、端末の Wi-Fi 受信量（`en0`）を測った結果:
    - 1,024px の要求: 1枚 約 0.82MB・0.69秒（受け取った画像を JPEG にし直すと 309KB で、以前の 287KB と合う）
    - 2,048px の要求: 1枚 約 0.81MB・0.61秒
    - **3,000px の要求（今の設定）: 1枚 約 1.87MB・0.84秒**
    - 2,048px 以下には同じ縮小版（約 0.8MB）が配られ、3,000px は縮小版では足りず元ファイル並みになる
    - 見積もり: iCloud のみ 2,198 枚で **約 4.1GB**（2,048px なら約 1.8GB）。3万枚なら約 56GB
    - 画面の「1枚あたり約300KB」は実態の約6分の1だったので、**「約2MB」に訂正**した
    - **2,048px に下げるかは保留**。端末にある本物の写真 879 枚を 3,000px と 2,048px で読み比べると、文字の所見がある写真が 10 枚 → 8 枚に減った（消えた所見は電話番号2・郵便番号1・メール1・住所1。増えた所見は無し）。合成画像では両者に差が無く（どちらも画像の高さの 1% 以上の文字を読める）、消えた所見の枠は画像の 8〜25% と大きいので、単純な解像度不足ではない。消えた2枚が正しい検出だったかを確認してから決める
  - **実機で分かった例外（2026-09-11）**: 2,600枚超のうち数枚は縮小版の生成が `PHPhotosErrorDomain -1` で落ちる。元ファイルで取り直すフォールバックを入れたが、それも落ちるものがあり、底のエラーは `CloudPhotoLibraryErrorDomain 25 "Record not found"` = **iCloud 側にその写真の実体が無い（孤児レコード）**。アプリ側でできることは無い。「取れなかった」記録のまま毎回再挑戦する（数枚 × 0.5秒でコストは無視できる。iCloud 側で復旧すれば自然に診断される）。取得の失敗理由は `os.Logger`（subsystem `com.upft.photodock`・category `PixelSource`）に出す。アセット ID や画像は出さない
- **取れなかった写真を「所見なし」として扱わない**。`Data?` の nil では「取れた・iCloud にある・消えた」が同じになり、iCloud 上の写真が ✅ として集計される（権限拒否と同じ偽の ✅）。pixelSource の戻り値は**3状態の enum**にする
- スキャン済み記録に「**未診断（ローカルに無い）**」として残す。次回ローカルに来ていれば診断対象になる。画面には「n 枚は iCloud にあるため診断できませんでした」と誠実に出す
- ~~**希望は「縮小版は端末にある」こと**~~ → **2026-09-10 実測で否定された**（iPhone 15 Pro Max・3,337枚・iCloud 最適化オン）
  - 元ファイルが端末にあるのは **655 枚（20%）**。残り **2,682 枚（80%）は iCloud のみ**
  - iCloud のみの標本 200 枚に、ネットワーク禁止で縮小版を要求した結果:

    | 要求 | 返った | 返った画像の長辺 |
    |---|---|---|
    | `.fastFormat`（今すぐ出せるもの） | 200/200 | **120px**（一覧用サムネイルと同じもの） |
    | `.highQualityFormat` 480px | 166/200（83%） | 480px |
    | `.highQualityFormat` 720px | 30/200（15%） | 720px |
    | `.highQualityFormat` 1,024px | 13/200（6.5%） | 1,024px |
    | 参考: 元ファイルあり 30 枚に 1,024px | 30/30 | 1,024px |

  - **端末に残る縮小版は長辺 480px が 83%、120px のサムネだけが 17%**。1170×2532 のスクショを 480px に縮めると UI 文字は高さ 6px 前後で、512px の前段実験で文字入りの 95% を落としたのと同じ領域。**通信ゼロで iCloud 分を診断するのは成立しない**
  - **帰結**: 「通信ゼロで全量診断」は端末にある 20% にしか言えない。残りは **Wi-Fi 接続時のダウンロードをオプトイン**で提供するしかない（Phase 2 検討 → **前に出す**）。ダウンロードの実測（同日・標本 20 枚・Wi-Fi）: 1,024px 要求で 20/20 成功、**287KB・0.50秒/枚**（長辺は 480〜1,024。ネットワークを許しても一部は 480px しか来ない）。元ファイルは 1.6MB・0.66秒/枚。上の「既定ではダウンロードしない」の項に帰結を記載

### 所見インデックス（保存の設計）

- **正体は「所見のリスト」ではなく「スキャン済み記録」**（2026-09-07 明文化）。**所見が0件だった写真も記録する**。記録しないと「未スキャン」と区別できず、カメラロールの大半（＝何も見つからない写真）が毎回再スキャンされて、2回目以降の短縮がまったく効かない
- 保存するのは **asset ID・所見の種類・severity・領域・modificationDate・適用済みスキャン品質・スキャン時の Vision 世代** のみ。**検出テキスト本文は保存しない**（「カード番号そのもの」は端末に残らない＝売り文句）
- インデックスは**ただのキャッシュ、真実は常に最新のスキャン**。再診断で差分が出たら上書き（自己修復）。写真が編集された（modificationDate 変化）→ 無効化して再スキャン
- **品質は単調に上がる**: 一括スキャンは「要求品質 > 記録品質、または編集済み」のアセットだけ処理（`ScanRecordPolicy.needsRescan`）。~~詳細画面は常に精密→上書き~~ → 2026-09-11: 全量が精密のみになったので詳細は再スキャンせず記録を表示する。高品質側が常に勝つ、という規則自体は将来解像度を上げるときのために Policy に残す
- 整合性の要: 品質ノブ（**解像度のみ**。recognitionLevel は `.accurate` 固定になったので軸から外れた）**以外**のパイプライン（言語・revision・座標変換・分類 Policy）は一括・詳細で同一＝**同一 UseCase を通す**
- **Vision の世代が変わったら再スキャン対象**（2026-09-07 追記）: 年2回の利用頻度だと、前回スキャンと今回の間に OS のメジャー更新が挟まるのが普通。品質ノブが同じでも検出結果は変わりうる（「検証済みの事実」の OCR 決定性の4要因のうち「OS の Vision 世代」）。世代を記録しないと「OS が賢くなったのに古い判定を信じ続ける」ことになる
- **判定ルールの版が変わっても再スキャン対象**（2026-11-25 決定）: 記録の「世代」を「OS の版 + 判定ルールの版」にした（`ScanRecordPolicy.generation`。値の例 `Version 26.2 (Build …)#rules1`）。それまでは OS の版だけだったので、判定ルールを直しても記録済みの写真は古い判定のままで、実機確認のときにアプリを入れ直す必要があった。保存の形式は変えていない（`generation` は元から文字列）。版は `FindingRules.version` で、**判定結果が変わる変更をしたら上げる**。上げ忘れは、代表的な45行の判定結果を固定したテスト（`FindingRulesVersionTests`）が検出する。版を入れる前の記録は世代が一致しないので、更新後の最初の診断で全件が一度だけ診断し直される
- asset ID（`PHAsset.localIdentifier`）は**端末ローカルで、端末間で共通ではない**。インデックスは移行できない＝「ただのキャッシュ」という位置づけと整合している（iCloud でのインデックス同期は成立しない）

### 対処（すべて元画像は非破壊 or システム確認つき）

- **削除**（システム確認ダイアログ経由）/ **非表示アルバムへ移動**（iOS 16+ は Face ID ロック付き）— 主対処
- **位置情報を除去したコピーの作成** — 位置情報所見の対処（脇役）
- 訴求は正確に: GPS は「メール・クラウド・ファイル送信で渡すたびに漏れる」、ピクセルは「どの経路でも消えない」

### 再接触の手段（Phase 2 以降・2026-09-07 に優先度を修正）

- **主は再診断リマインダー（ローカル通知）**: 「前回の診断から6ヶ月です」。歯科検診と同じ構造で、人間ドックのフレーミングと完全に一致する。常駐監視ではないので「やらないこと」に触れない。年2回しか起動されないアプリにとって、思い出してもらう仕組みは機能そのもの
- **App Intent「最新の写真をチェック」は優先度を下げる**: コントロールセンター / アクションボタン / オートメーションは「**毎日その瞬間に使う機能**」で、経緯 2. で却下した習慣化の発想に戻っている。価値の根拠が「UseCase が UI 非依存であることの実演」（＝学習目的）に寄っていることを自覚して扱う。やらないとは決めていないが、リマインダーより後
- View / Extension / Intent が同じ UseCase を呼ぶ構造自体は維持する（層設計の帰結であり、機能の優先度とは別）

## UI 原則（3つ）

1. **分類を説明しない、結果に埋め込む**。「EXIF とは」の講義画面は作らない。ユーザーの問いは「見られたらまずい写真はどれ？」だけ
2. **経路チップで教える**。各検出カードに「どこで漏れるか」: `[メール ⚠️残る] [LINE(ファイル) ⚠️] [X ✅消える]`（EXIF 系）/ ピクセル系は全経路⚠️。検出種別→経路リストは純粋関数 **→ 2026-11-26: 当面は文で出す**（ピクセル系しか検出していないあいだは、チップが全部同じになるため。「段階2で決めたこと」参照）
3. **待ち時間を体験にする**。第1段の即答＋所見のライブ積み上げで、スキャンの数十分を「診断が進んでいる」実感に変える

その他: 元画像は絶対に編集しない / スキャンは自動・明示操作は最小 / severity は断定調を避ける / 何も見つからないときは「✅ 問題ありません」を最短で返す

## 設計方針（アーキテクチャ）

- サンプル repo と同じ4層 + DI 3値。恒常ルール5か条は CLAUDE.md
- **対応 OS は iOS 26 以上**（2026-09-12 決定・それまでは 18.0）。バックグラウンド継続（`BGContinuedProcessingTask`）と Foundation Models がどちらも iOS 26 必須で、`#available` で二重の実装を持つ価値が無い。検証実機（iPhone 15 Pro Max）は iOS 26.6。iOS 18 に留まる利点は対応端末の広さだけで、半年に1回使うアプリの初期段階では優先しない
- `Core/` は Foundation のみ → **CoreLocation も import 不可**。クラスタリング用に独自 `GeoCoordinate`（緯度経度 Double）を Core に置く。画像は `Data` で UseCase に渡す（CGImage 化は Infrastructure の責務）
- `Region` は Core の独自型（**左上原点・0...1 正規化**）。Vision の左下原点との変換は Infrastructure の責務
- 写真の入力は依存にしない（`PhotosPicker` は権限不要の UI 部品）
- 顔データの保存・照合はやらない
- 想定依存（初期）: photoLibrary（メタデータ列挙+権限）/ pixelSource（画像データ取得）/ ocr / codes / faces / metadata(ImageIO) / findingStore（所見インデックス永続化）/ assetActions（削除・非表示・GPS除去コピー）あたり。実装しながら絞る
- Policy 候補: 検出分類（正規表現/Luhn）/ severity 判定 / マスク文字列生成 / 経路チップ対応表 / 座標クラスタリング / 残り時間推定 / スキャン優先度づけ

## マネタイズ（2026-09-07 時点・未決定）

年2回しか起動されない前提から、取れる形が制約される。

- **サブスクは合わない**: 使っていない期間に払い続ける体感になる。年2回のアプリで月額・年額は成立しにくい
- **候補**: ①買い切り ②無料で診断（第1段＋第2段）まで見せて、対処（削除・非表示の一括実行）や精密診断を課金で解放 ③完全無料
- **②を採るなら慎重に**: 「危険が n 件見つかりました。対処するには課金」は**不安を売る形**になり、審査でも嫌われやすい。UI 原則の「断定調を避ける」とも緊張する。診断結果を見せた後に対処を有料化する設計は、文言と価格の両方を詰める必要がある
- **決めるのは Phase 1 の TestFlight の後**: 「実際に何件見つかるか」を見てから。何も見つからない人が多数なら（brief は「それが最頻の価値」と書いている）課金は成立しない
