# PrivacyLens プロダクトブリーフ（2026-09-01 時点の決定事項）

SwiftArchitectureSample のセッションでの製品検討の結論。**このファイルが方針の原本**。
変更するときはこのファイルを更新する（会話の記憶はセッションを跨がない）。

## 1行定義

**写真のプライバシー診断アプリ。カメラロールの位置情報を地図で可視化して自覚させ、1枚単位では写り込み（写っている文字・顔・QR）を診断する。何も編集しない・何も保存しない・通信しない。**

## ここに至った経緯（結論だけ）

1. 初案は「SNS 投稿前の写り込みチェッカー」（共有シートでぼかして保存）
2. → **投稿前の習慣化は無理筋**と判断（リスクがまれで見えない / 投稿の瞬間は急いでいる / 必要な人ほど入れない逆選択）。ぼかし編集も却下（モザイク写真は投稿したくない・自然な対処はトリミングか撮り直しでありユーザーが自分でできる）
3. → **「予防」から「診断」へピボット**。一度きりの健康診断体験に振り切る。習慣不要・1回で価値が完結・結果画面がシェアされうる

## 検証済みの事実（前セッションで確認済み。再調査不要）

- **主要 SNS（X / Instagram / Facebook / メルカリ）はアップロード時に EXIF（GPS 含む）を除去する**。「SNS に上げた写真から GPS で自宅バレ」は基本成立しない＝そう訴求したら嘘になる
- **GPS が残る経路**: メール添付・Slack・Google Drive / Dropbox・AirDrop・LINE の「ファイルとして送信」・個人ブログ等（ファイルがファイルのまま渡る経路）
- **二層の脅威モデル**（アプリの説明の背骨）:
  - ファイルで渡す → **位置情報（EXIF GPS）** が漏れる
  - SNS に上げる → メタデータは消えるが**ピクセルに写っているもの**（住所・電話・ナンバー・顔・QR）は誰にも消せない
- **Vision の顔検出はシミュレータで動かない**（code 9）。実機のみ。環境依存の検出器は「検出ゼロで続行」に設計する（サンプル repo の `VisionInferenceService` に前例あり）
- **顔の個人識別（他人かどうか）は公開 API に存在しない**。PhotoKit のピープルアルバムも非公開。「顔がある」までしか分からない
- **他アプリの投稿ボタンへの介入・常駐監視は iOS では不可能**
- `PHAsset.location` は**メタデータだけで取れる＝画像を読まずに数万枚を数秒でスキャン可能**（地図診断の技術的根拠）
- スクリーンショットのレンダリング済みテキストは OCR がほぼ確実に読める（実写の斜め文字より遥かに強い）

## 機能構成

### 主役: カメラロール位置情報診断（地図）

- 全アセットの `PHAsset.location` をスキャン →「**位置情報付きの写真が n 枚あります**」→ 撮影場所を地図にピン表示
- ピンの密集地 →「自宅の可能性が高い場所」の推定 = **座標クラスタリングの純粋関数 → `Core/Policy`**（このアーキテクチャの見せ場）
- 対処: 位置情報を除去したコピーの一括作成
- 訴求は正確に:「SNS でバレる」ではなく「**メール・クラウド・ファイル送信で写真を渡すたびに漏れる**」

### おまけ: 1枚精査（写り込み診断）

- OCR（`VNRecognizeTextRequest` ja+en）→ Policy が正規表現/チェックサムで分類: 電話番号・住所・郵便番号・メール・カード番号（Luhn）・ナンバープレート書式
- 顔検出（実機のみ・「情報」として提示。断定しない:「顔が n 件写っています — ご自身や同意のある方なら問題ありません」）
- 「写り込みらしさ」ヒューリスティック = 顔の**サイズ・位置（端）・向き（yaw）**から背景の写り込みらしさをスコアリング → 純粋関数で Policy に
- QR / バーコード（`VNDetectBarcodesRequest`・ペイロードの中身を見せる）
- EXIF GPS の有無

### 入口（Phase 2 以降）

- App Intent「最新の写真をチェック」1本で: コントロールセンター（iOS 18）/ アクションボタン / ウィジェット / **ショートカットのオートメーション（「X を開いたとき」に自動実行）** を全部賄う
- UseCase が UI 非依存であることの実演（View / Extension / Intent が同じ `ScanImageUseCase` を呼ぶ）

## UI 原則（3つ）

1. **分類を説明しない、結果に埋め込む**。「EXIF とは」の講義画面は作らない。ユーザーの質問は常に「これ、渡して大丈夫？」だけ
2. **経路チップで教える**。各検出カードに「どこで漏れるか」を並べる: `[メール ⚠️残る] [LINE(ファイル) ⚠️] [X ✅消える]`。二層モデルはこの1行に圧縮する
3. **地図が説明のすべて**。自宅にピンが密集した地図に説明文は要らない

その他: 元画像は絶対に触らない（常にコピー）/ スキャンは自動・明示操作は最小 / 検出の severity は断定調を避ける（顔は「注意」止まり）/ 何も見つからないときは「✅ 問題ありません」を3秒で返す（これが最頻の価値）

## 設計方針（アーキテクチャ）

- サンプル repo と同じ4層 + DI 3値。恒常ルール5か条は CLAUDE.md
- `Region` は Core の独自型（**左上原点・0...1 正規化**）。Vision の左下原点との変換は各 Infrastructure 実装の責務（座標バグを型で殺す）
- 写真の入力は依存にしない（`PhotosPicker` は権限不要の UI 部品。UseCase には入力が引数で渡る）
- **診断履歴を保存しない**（「何が写っていたか」自体が機微情報）。「あえて保存しない」を README に書く
- 顔データの保存・照合はやらない（v2 でも慎重に）。「顔データを保存しない」は売りになる
- 想定依存（初期）: photoLibrary（アセット列挙+location）/ ocr / faces / codes / metadata(ImageIO) / geoWriter（GPS除去コピー）あたり。実装しながら絞る

## フェーズ計画

| Phase | 内容 | 出口 |
|---|---|---|
| 0 | スパイク: ①実写真での OCR 精度（斜め・小さい住所文字）②`PHAsset.location` の大量スキャン速度 ③SNS 各社の EXIF 挙動の実地再確認（上げて保存して確認・1時間で可能） | 技術リスクの確定 |
| 1 | MVP: 地図診断 + GPS 除去コピー + 1枚精査（OCR/QR/EXIF。顔は実機 TestFlight で） | TestFlight |
| 2 | App Intent（コントロールセンター/アクションボタン/オートメーション） | **App Store リリース** |
| 3 | Share Extension / 人名検出（NLTagger）/ String Catalog / スクショ特化モード（配信者向け）の検討 | v1.1 |

## リリース準備（Phase 1〜2 で並行）

- Apple Developer Program 加入
- 権限: 写真は **limited library 対応必須**・保存は「追加のみ」権限 / プライバシーマニフェスト（オンデバイス完結・収集なし）
- App Store 審査観点: 診断系の文言は断定を避ける（「特定される」ではなく「特定につながる可能性」）
- 名前「PrivacyLens」は仮。リリース前に決定

## やらないことリスト（再提案しない）

- 投稿ボタンへの介入・常駐監視（iOS で不可能）
- ぼかし・モザイク編集（却下済み。将来やるなら「顔だけスタンプ」を v1.1 以降で再検討）
- 顔の個人識別・本人登録
- 診断履歴の保存
- バックエンド・アカウント・通信
