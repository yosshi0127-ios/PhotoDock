# PhotoDock / 写真ドック プロダクトブリーフ（2026-09-07 更新）

製品検討セッションの結論。**このファイルが方針の原本**。
変更するときはこのファイルを更新する（会話の記憶はセッションを跨がない）。

## 1行定義

**カメラロールの棚卸し診断アプリ。全量スキャンで「見られたらまずい写真」（カード・住所・電話・スクショ内の個人情報・QR・位置情報）を洗い出し、危険度順に提示して対処（削除・非表示・位置情報除去コピー）までさせる。何も編集しない・検出内容の本文を保存しない・通信しない。**

## ここに至った経緯（結論だけ）

1. 初案は「SNS 投稿前の写り込みチェッカー」（共有シートでぼかして保存）
2. → **投稿前の習慣化は無理筋**と判断（リスクがまれで見えない / 投稿の瞬間は急いでいる / 必要な人ほど入れない逆選択）。ぼかし編集も却下
3. → 「予防」から「診断」へピボット。当初は**位置情報の地図可視化を主役**にした
4. → 再検討（2026-09-01）で**主役を「全量棚卸しスキャン」に交代**。理由: ①GPS の脅威は薄い（主要 SNS が EXIF を消す以上、漏れる経路はファイル送信だけ＝作者自身が脅威を感じられない）②地図の結果画面は自宅の位置そのものでシェアできない ③本当の爆弾はピクセル内の機微情報（カードを写した写真・身分証・書類・パスワードのスクショ）で、漏洩経路も共有に限らない（紛失・覗き見・誤送信）。ユーザーの問いを「これ、渡して大丈夫？」から「**カメラロールに、見られたらまずい写真が眠っていないか？**」に変更
5. → 実装着手後（2026-09-07）に**利用頻度を明示化**。このアプリは毎日使うものではなく「**半年に1回、気づいたときに回す**」人間ドック型。これは方針転換ではなく 3. の帰結の言語化で、以下が導かれる:
   - **初回スキャンが製品のほぼ全体**。2回しか起動されないなら学習の余地がなく、オンボーディングで説明する猶予もない。待ち時間 UX（UI 原則 3.）は装飾ではなく本体
   - **2回目は別の体験（差分診断）**になる（後述）
   - **再接触の手段は通知**であってウィジェットやコントロールセンターではない（「入口」節で優先度を修正）
   - **課金にサブスクは合わない**（「マネタイズ」節）
   - 半年空くと **OS のメジャー更新が挟まる**のが普通＝所見インデックスに Vision の世代が必要（後述）

## 検証済みの事実（前セッションで確認済み。再調査不要）

- **主要 SNS（X / Instagram / Facebook / メルカリ）はアップロード時に EXIF（GPS 含む）を除去する**。「SNS に上げた写真から GPS で自宅バレ」は基本成立しない＝そう訴求したら嘘になる
- **GPS が残る経路**: メール添付・Slack・Google Drive / Dropbox・AirDrop・LINE の「ファイルとして送信」・個人ブログ等（ファイルがファイルのまま渡る経路）
- **二層の脅威モデル**（経路チップの根拠）:
  - ファイルで渡す → **位置情報（EXIF GPS）** が漏れる
  - SNS に上げる → メタデータは消えるが**ピクセルに写っているもの**は誰にも消せない
- **Vision の顔検出はシミュレータで動かない**（code 9）。実機のみ。環境依存の検出器は「検出ゼロで続行」に設計する
- **顔の個人識別（他人かどうか）は公開 API に存在しない**。「顔がある」までしか分からない
- **他アプリの投稿ボタンへの介入・常駐監視は iOS では不可能**
- `PHAsset` のメタデータ（`location` / `mediaSubtypes` / `creationDate`）は**画像を読まずに数万枚を数秒でスキャン可能**（第1段スキャンの技術的根拠）
- スクリーンショットのレンダリング済みテキストは OCR がほぼ確実に読める（実写の斜め文字より遥かに強い）
- **`VNRecognizeTextRequest` はシミュレータで動く**（2026-09-07 実測・iOS 18.4）。顔検出（code 9 で動かない）と違って推論が通るので、**第2段の開発ループはシミュレータで回せる**
  - レンダリング済みの文字（スクショ相当）は日本語の住所を含めて**確度 1.000** で読めた。1,000×700 の画像・4行で 1.5 秒未満
  - `boundingBox` は Vision の**左下原点・0...1 正規化**。画像上端の行が `y≈0.83` で返る。`Region`（左上原点）への変換は **`y' = 1 - (y + height)`**（実測で確認）
  - 認識は**行単位**で返り、`4111 1111 1111 1111` のように**空白と区切り記号がそのまま保持される**。Luhn・電話番号・郵便番号の判定は**正規化（空白とハイフンの除去）してから**行う
- OCR は乱数を使わない推論＝**同一入力・同一設定・同一 OS なら実用上決定的**。結果が変わる要因は「入力解像度 / recognitionLevel / OS の Vision 世代 / 写真自体の編集」の4つだけ
- **`.fast` は日本語を扱えない**（2026-09-07 実測・iOS 18.4）。`supportedRecognitionLanguages` の結果:
  - `.fast` = 6言語・**ラテン文字系のみ**（`en-US` `fr-FR` `it-IT` `de-DE` `es-ES` `pt-BR`）。日本語・中国語・韓国語なし
  - `.accurate` = 18言語（`ja-JP` `zh-Hans` `zh-Hant` `ko-KR` `ru-RU` `th-TH` `ar-SA` 等を含む）
  - `VNRecognizeTextRequest.supportedRevisions` = `[1, 2, 3]` / `currentRevision` = 3
  - **帰結: recognitionLevel は常に `.accurate` 固定**。品質ノブは「入力解像度」と「対象範囲」だけになる（プリセットの定義を後述のとおり変更）
- **`VNDetectTextRectanglesRequest` を OCR の前段に置くと 3.1 倍速**（2026-09-10 実測・162枚・1170x2532・シミュレータ）。**採用済み**（`VisionOCRService` の内側。protocol は変えていない）
  - 大半の写真には文字が無く（162枚中 119枚）、OCR はそこで「探して何も見つけない」ために 270ms 使っていた。矩形検出は**読まずに文字らしい矩形の有無だけ**を見るので **15ms（OCR の 6%）**。言語非依存なので `.fast` のように日本語で困らない
  - **見逃しは実質ゼロ。** 唯一「文字ありなのに矩形0」になった1枚は、OCR が模様を「■」（確度 0.30）と誤認したもので、Policy の確度閾値 0.5 で捨てられる行だった。無駄（文字なしなのに矩形あり）は2枚
  - **512px では使えない**（文字ありの 41/43 を落とす）。前段の解像度は OCR と同じ `maxPixelSize` を使う。判定に失敗したら OCR に回す（見逃す方向に倒さない）
  - 帰結: 3万枚の見積もりは 約2時間 → **約40分**。中断・再開が必須という結論は変わらない

## 機能構成

### 主役: 全量プライバシースキャン（二段構え）

- **第1段（数秒で完了）**: メタデータのみ全件列挙 — 位置情報付き枚数・スクショ枚数・総枚数。起動直後に「結果のある画面」を出し、第2段の計画（優先キュー・所要時間見積もり）を作る
- **第2段（漸進・進捗つき）**: ピクセルスキャンを優先度順に — **スクショ最優先**（機微情報の密度が最も高く OCR が最も効く）→ 直近 → 残り
  - OCR（`VNRecognizeTextRequest` ja+en）→ Policy が正規表現/チェックサムで分類（種類の一覧と段階は「検出する種類」を参照）
  - QR / バーコード（`VNDetectBarcodesRequest`・ペイロード分類）
  - EXIF GPS の有無
  - **N 枚を並行処理し、完了順に記録する**（2026-09-07 決定）。~~逐次より圧倒的に速い~~ → **2026-09-10 の実測で「ほぼ速くならない」ことが判明**（下記）。完了順に流す仕組み自体は進捗表示と中断のために残す
  - **並列度の実測（2026-09-10・162枚 / 1170x2532 / iPhone 16 シミュレータ）**

    | 同時実行数 | 所要 | 1枚あたり | |
    |---|---|---|---|
    | 1 | 44.5 秒 | 274 ms | 基準 |
    | **2** | **41.5 秒** | **256 ms** | 7% 改善。**既定値はこれ** |
    | 4 | 41.4 秒 | 255 ms | 変化なし |
    | 8 | **数分経っても終わらない** | — | **破綻**（テストとアプリの両方で再現） |

    **Vision が内部で全コアを使うので、外側の並列化はほぼ効かない。** 増やすと画像のデコードと推論コンテキストが同時に載ってメモリで破綻する。実際の写真は 4032x3024 とさらに大きいので、**実機ではより少ない同時実行数で危険域に入る**とみるべき。`ProcessInfo.thermalState` 連動を検討する前に、まず「増やしても速くならない」という前提に立つこと
  - **3万枚の見積もり: 256ms × 30,000 = 約2時間8分。** 一度で終わらせる設計は成り立たず、中断・再開が必須（下記の方針が正しかったことが数字で裏づけられた）
  - 全件を一度に `addTask` しない（3万タスクを作ることになる）。同時実行数を保ちながら「1つ完了したら次を1つ投入」で流す
  - 優先度は**投入順**で守る。完了順は前後するので、ライブ積み上げの表示順は厳密には優先度順にならない（投入が優先度順なら「スクショから先に結果が出る」体験は保たれるので実害なし）
- **スキャン設定**（2026-09-07 に `.fast` 非対応の実測を受けて改訂）: プリセット2つ「クイック診断」（**accurate × 低解像度**）/「精密診断」（**accurate × 高解像度**）＋対象範囲（すべて / スクショのみ / 期間）。**recognitionLevel は両方 `.accurate` 固定**で、プリセット間の速度差は**縮小率だけ**で作る（対象範囲はプリセットとは独立したユーザーの選択）。Vision の用語は UI に出さない。モード選択時に推定時間を表示（枚数 × モード別の1枚あたり実測シード値）
  - 対象範囲（すべて / スクショのみ / 期間）は**ユーザーが選ぶフィルター**として提供する。**既定は常に「すべて」で、全量を諦める方向の設計変更はしない**（2026-09-07 決定）。カードを写した写真・身分証・書類は**スクショではなく撮影画像**であり、そこを外すと1行定義が崩れる
  - `.fast` を失った速度は「対象を減らす」以外で埋める: ①**入力解像度の縮小**（精度とのトレードオフを Phase 0 で測る）②**並列度**（複数枚を同時に OCR。TaskGroup で同時実行数を制御。上限は熱と電力の制約を実機で測って決める）③**漸進提示**（優先キュー順に結果を先に出す＝待ち時間を体験にする既存方針）④**中断・再開**（一度で終わらせる必要をなくす）
- **診断中の表示**: 残り枚数 / 総枚数・残り時間（**実効スループット**＝直近の一定期間に完了した枚数 ÷ 経過時間、× 残り枚数。純粋関数 → Policy）・**所見のライブ積み上げ**（「危険 n 件」がスキャン中に増えていく）
  - 「1枚あたりの所要時間の移動平均 × 残り枚数」**ではない**（2026-09-07 修正。並行処理では1枚あたりの時間が同時実行数の分だけ伸びるので、そのまま掛けると**同時実行数の倍だけ過大に見積もる**。「あと40分」と出して10分で終わる表示になる）
    - **2026-09-10 追記: この懸念は実際には起きない。** 並列化がほぼ効かない（上記の実測）ため、同時実行数を上げても1枚あたりの時間は伸びない（274ms → 256ms）。**素直に「完了枚数 ÷ 経過時間 × 残り枚数」でよい**。ただし式の形は実効スループット方式のまま維持する（並列が効く環境に変わっても壊れないため）
- **中断・再開**: 所見インデックスがチェックポイントを兼ね、未スキャン分から再開。長時間スキャンはフォアグラウンド前提（バックグラウンドはサスペンドされる。スキャン中は画面スリープ抑止）
  - 並行処理なので「どこまで進んだか」の数字では表せない（5枚目が済んで3枚目が未完という状態が普通に起きる）。「**記録がある = 済み**」の集合で表すので順序は不要
  - **1アセット1トランザクション**で書く。途中で落ちても部分書き込みが残らないようにする（冪等なので、書けていない分は次回そのまま再スキャンされる）

### 結果画面: 3階層ドリルダウン

```
診断ホーム（サマリー: 危険 n / 要注意 m / 位置情報付き k）
├─ 危険・要注意 ─▶ 該当写真グリッド（サムネ＋所見バッジ）─▶ 写真詳細 ─▶ 対処
└─ 位置情報     ─▶ 地図（クラスタ）─▶ 場所別グリッド ─▶ 写真詳細
```

- **写真詳細＝単発再診断画面**: 開いた瞬間にその1枚を**常に精密設定で**再スキャンし（1枚なら精密でも1秒程度）、写真上に検出領域の枠をオーバーレイ（`Region` 型の使い道）。所見リスト（severity・経路チップ）と対処ボタン
- **検出テキストはマスク表示**（`**** **** **** 1234`）。診断アプリ自身が漏洩源にならない。マスク文字列の生成は Policy
- 地図は「位置情報所見のドリルダウン」として存続（主役から降格）。ピン密集地の推定は座標クラスタリングの純粋関数 → `Core/Policy`。文言は断定しない（「よく撮影している場所」）
- PhotosPicker からの単発診断も入口として残す（「これから渡す1枚」のチェック。顔検出＋写り込みらしさヒューリスティックはこの文脈のみ）
- **2回目以降の起動は「差分診断」**（2026-09-07 追記）: 半年ぶりに開けば大半が未スキャンの新規写真。最初に出すべきは「**前回の診断から 1,204 枚増えました**」であって、いきなり全体サマリーではない。所見インデックスがあるので差分は算出できる。上の3階層ドリルダウンに無い画面なので、Phase 2 で追加する

### 検出する種類（2026-09-08 決定・段階的に増やす）

**第1弾（OCR だけで判定できるもの・7種類）**

| ケース | 判定 | 誤検出 |
|---|---|---|
| `cardNumber` | 桁数 + **Luhn** | 極小 |
| `identityDocumentNumber` | **マイナンバー12桁・免許証12桁はチェックデジットあり**。パスポートは書式（英字2+数字7） | 小 |
| `credential` | **1行内のラベル語**（パスワード / Password / KEY / 暗号化キー / PIN 等）。付箋やルーターのラベルは1行で読める | 中 |
| `phoneNumber` | 桁数と書式 | 小 |
| `email` | 書式 | 小 |
| `postalCode` | `123-4567` | 中 |
| `address` | 都道府県 + 市区町村 | **大**（看板・広告・地図アプリのスクショに当たる） |

**第2弾（判定手法の課題あり）**: `dateOfBirth` / `bankAccountNumber` / `medicalInformation`。
書式だけでは判定できない（生年月日は撮影日や賞味期限と区別できない、口座番号は7桁でチェックサムがない、病歴は書式が存在しない）。「**ラベル語との共起**」で判定する必要があり、`[RecognizedText]` の**行の並びと位置関係**を見る形になる。手法を確立してから追加する。

**第3弾（別の依存が必要）**: `barcode`（`codes` = `VNDetectBarcodesRequest`）/ `face`（`faces`・シミュレータで動かない・Phase 1.5）。
`barcode` は価値が高い（搭乗券やチケットのバーコードに氏名・座席・予約番号が入っていて、SNS 投稿からの実被害例がある）。

**見送り**: `accountIdentifier`（SNS やゲームの ID は形が定まっておらず、任意の英数字列と区別できない＝誤検出が支配的）/ `personName`（`NLTagger` で検出可能だが、名刺・ポスター・看板に無数に写っていて**単体では価値が低い**）/ `licensePlate`（書式が他の文字列に当たりやすく、しかも**写っているのが他人の車**かもしれない）。

**`credential` だけは網羅が原理的に不可能（2026-09-09 実測を経て確定）**

他の6種類は「値そのもの」で判定できる（Luhn・書式・地名）。`credential` だけは**値に決まった形がない**ので周りのラベル語に頼るしかなく、ラベルの表記は無限にある（`PW` / `合言葉` / `暗証` / `ログイン情報` / `Kennwort`…）。辞書を育てても追いつかない。

**ベクトル（意味の近さ）で表記揺れを吸収する案は実測して却下した。**

| 実測 | 結果 |
|---|---|
| `NLEmbedding.wordEmbedding(for: .japanese)` | **nil**（iOS 18.4 シミュレータ / macOS ともに日本語モデルが存在しない） |
| `NLEmbedding.sentenceEmbedding(for: .japanese)` | **nil**（同上） |
| 英語の単語埋め込みでの分離 | **分離しない**。`password` からの距離が `login` 1.01 < `address` 1.07 < `passcode` 1.08 < `credential` 1.14 < `secret` 1.23。**「住所」が「パスコード」より近い**ので閾値を引けない |

単語埋め込みは「同じ文脈に共起する語」を近くするだけで、「機微かどうか」では分離しない。入力フォームの文脈で `password` と `address` は隣り合う。

**採る手（この順）**

1. **正規化で表記の揺れを吸収する** — 小文字化・空白除去に加えて全角→半角・記号除去。ラベル1語 `apikey` で `API_KEY` / `api-key` / `Ａｐｉキー` / `API KEY` を拾える。**別の語（`合言葉`）は拾えない**
2. **値の書式で拾う（ラベル不要）** — `sk-` / `ghp_` / `AKIA` / `xoxb-` / `eyJ`(JWT) / `-----BEGIN ... KEY-----`。機械が発行するトークンはプレフィックスが業界固有なので、誤検出ほぼゼロで確実に拾える
3. 保留: 弱い証拠の組み合わせ（短いラベル語 + 同じ行の高エントロピー文字列）。誤検出との境目が実データなしに決められない
4. 将来: Create ML のテキスト分類（日本語可・要訓練データ）/ Foundation Models（iOS 26 が必要でターゲット外）

**見逃しは「安全」の誤ったお墨付きになる。** ゼロ件の表示は必ず「見つかりませんでした」とし、「安全です」と断定しない（UI 原則の「断定調を避ける」がここに効く）。

**2つの原則**

- **severity は検証可能性で決める**（恣意的に割り当てない）。チェックサムが通ったもの（カード番号・マイナンバー・免許証番号）は「写っています」と**断定してよい**。書式が一致するだけのもの（郵便番号・住所・パスポート番号）は「〜のような文字列が写っています」に留める。UI 原則「断定調を避ける」を、種類が増えても一貫した基準で満たせる
- **組み合わせで危険度が上がる**。氏名・生年月日は単体ではほぼ無害だが、**氏名 + 生年月日 + 住所が同じ写真に揃えば本人確認書類**。severity を「kind ごとの固定値」ではなく「同じ写真に何が揃っているか」で決める複合判定が必要になる（brief の「判断ルールが増えたら Policy 行き」に該当）

### iCloud 最適化への対応（2026-09-07 決定・製品の分かれ目）

「iPhone のストレージを最適化」がオンだと**端末に元ファイルがなく、縮小版しか残らない**（写真アプリで古い写真を開くとロードが走るのがこれ）。写真が多い人ほどこの設定なので、**例外ケースではなく多数派の状態**として扱う。

- **既定ではダウンロードしない**（`isNetworkAccessAllowed = false`）。1枚3MB × 3万枚 = 90GB で現実的でなく、「通信しない」という売りとも正面からぶつかる。「Wi-Fi 接続中に限りダウンロードして診断」のオプトインは Phase 2 以降の検討
- **取れなかった写真を「所見なし」として扱わない**。`Data?` の nil では「取れた・iCloud にある・消えた」が同じになり、iCloud 上の写真が ✅ として集計される（権限拒否と同じ偽の ✅）。pixelSource の戻り値は**3状態の enum**にする
- スキャン済み記録に「**未診断（ローカルに無い）**」として残す。次回ローカルに来ていれば診断対象になる。画面には「n 枚は iCloud にあるため診断できませんでした」と誠実に出す
- **希望は「縮小版は端末にある」こと**。クイック診断は低解像度で走らせる設計なので、縮小版で OCR が通るなら**全ユーザーが通信ゼロで全量診断できる**。通らなければ iCloud 最適化ユーザーは部分診断に留まる。住所やカード番号は解像度が効くので楽観できない → **Phase 0 の最重要項目**

### 所見インデックス（保存の設計）

- **正体は「所見のリスト」ではなく「スキャン済み記録」**（2026-09-07 明文化）。**所見が0件だった写真も記録する**。記録しないと「未スキャン」と区別できず、カメラロールの大半（＝何も見つからない写真）が毎回再スキャンされて、2回目以降の短縮がまったく効かない
- 保存するのは **asset ID・所見の種類・severity・領域・modificationDate・適用済みスキャン品質・スキャン時の Vision 世代** のみ。**検出テキスト本文は保存しない**（「カード番号そのもの」は端末に残らない＝売り文句）
- インデックスは**ただのキャッシュ、真実は常に最新のスキャン**。再診断で差分が出たら上書き（自己修復）。写真が編集された（modificationDate 変化）→ 無効化して再スキャン
- **品質は単調に上がる**: 一括スキャンは「要求品質 > 記録品質、または編集済み」のアセットだけ処理（精密一括はクイック記録分だけ再処理・詳細画面で精密済みならスキップ）。詳細画面は常に精密→上書き。高品質側が常に勝つ
- 整合性の要: 品質ノブ（**解像度のみ**。recognitionLevel は `.accurate` 固定になったので軸から外れた）**以外**のパイプライン（言語・revision・座標変換・分類 Policy）は一括・詳細で同一＝**同一 UseCase を通す**
- **Vision の世代が変わったら再スキャン対象**（2026-09-07 追記）: 年2回の利用頻度だと、前回スキャンと今回の間に OS のメジャー更新が挟まるのが普通。品質ノブが同じでも検出結果は変わりうる（「検証済みの事実」の OCR 決定性の4要因のうち「OS の Vision 世代」）。世代を記録しないと「OS が賢くなったのに古い判定を信じ続ける」ことになる
- asset ID（`PHAsset.localIdentifier`）は**端末ローカルで、端末間で共通ではない**。インデックスは移行できない＝「ただのキャッシュ」という位置づけと整合している（iCloud でのインデックス同期は成立しない）

### 対処（すべて元画像は非破壊 or システム確認つき）

- **削除**（システム確認ダイアログ経由）/ **非表示アルバムへ移動**（iOS 16+ は Face ID ロック付き）— 主対処
- **位置情報を除去したコピーの作成** — 位置情報所見の対処（脇役）
- 訴求は正確に: GPS は「メール・クラウド・ファイル送信で渡すたびに漏れる」、ピクセルは「どの経路でも消えない」

### 再接触の手段（Phase 2 以降・2026-09-07 に優先度を修正）

- **主は再診断リマインダー（ローカル通知）**: 「前回の診断から6ヶ月です」。歯科検診と同じ構造で、人間ドックのフレーミングと完全に一致する。常駐監視ではないので「やらないこと」に触れない。年2回しか起動されないアプリにとって、思い出してもらう仕組みは機能そのもの
- **App Intent「最新の写真をチェック」は優先度を下げる**: コントロールセンター / アクションボタン / オートメーションは「**毎日その瞬間に使う機能**」で、経緯 2. で却下した習慣化の発想に戻っている。価値の根拠が「UseCase が UI 非依存であることの実演」（＝学習目的）に寄っていることを自覚して扱う。やらないとは決めていないが、リマインダーより後
- View / Extension / Intent が同じ UseCase を呼ぶ構造自体は維持する（層設計の帰結であり、機能の優先度とは別）

## UI 原則（3つ）

1. **分類を説明しない、結果に埋め込む**。「EXIF とは」の講義画面は作らない。ユーザーの問いは「見られたらまずい写真はどれ？」だけ
2. **経路チップで教える**。各検出カードに「どこで漏れるか」: `[メール ⚠️残る] [LINE(ファイル) ⚠️] [X ✅消える]`（EXIF 系）/ ピクセル系は全経路⚠️。検出種別→経路リストは純粋関数
3. **待ち時間を体験にする**。第1段の即答＋所見のライブ積み上げで、スキャンの数十分を「診断が進んでいる」実感に変える

その他: 元画像は絶対に編集しない / スキャンは自動・明示操作は最小 / severity は断定調を避ける / 何も見つからないときは「✅ 問題ありません」を最短で返す

## 設計方針（アーキテクチャ）

- サンプル repo と同じ4層 + DI 3値。恒常ルール5か条は CLAUDE.md
- `Core/` は Foundation のみ → **CoreLocation も import 不可**。クラスタリング用に独自 `GeoCoordinate`（緯度経度 Double）を Core に置く。画像は `Data` で UseCase に渡す（CGImage 化は Infrastructure の責務）
- `Region` は Core の独自型（**左上原点・0...1 正規化**）。Vision の左下原点との変換は Infrastructure の責務
- 写真の入力は依存にしない（`PhotosPicker` は権限不要の UI 部品）
- 顔データの保存・照合はやらない
- 想定依存（初期）: photoLibrary（メタデータ列挙+権限）/ pixelSource（画像データ取得）/ ocr / codes / faces / metadata(ImageIO) / findingStore（所見インデックス永続化）/ assetActions（削除・非表示・GPS除去コピー）あたり。実装しながら絞る
- Policy 候補: 検出分類（正規表現/Luhn）/ severity 判定 / マスク文字列生成 / 経路チップ対応表 / 座標クラスタリング / 残り時間推定 / スキャン優先度づけ

## マネタイズ（2026-09-07 時点・未決定）

年2回しか起動されない前提から、取れる形が制約される。

- **サブスクは合わない**: 使っていない期間に払い続ける体感になる。年2回のアプリで月額・年額は成立しにくい
- **候補**: ①買い切り ②無料で診断（第1段＋第2段）まで見せて、対処（削除・非表示の一括実行）や精密診断を課金で解放 ③完全無料
- **②を採るなら慎重に**: 「危険が n 件見つかりました。対処するには課金」は**不安を売る形**になり、審査でも嫌われやすい。UI 原則の「断定調を避ける」とも緊張する。診断結果を見せた後に対処を有料化する設計は、文言と価格の両方を詰める必要がある
- **決めるのは Phase 1 の TestFlight の後**: 「実際に何件見つかるか」を見てから。何も見つからない人が多数なら（brief は「それが最頻の価値」と書いている）課金は成立しない
